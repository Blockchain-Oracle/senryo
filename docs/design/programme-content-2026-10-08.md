Read the retained-family requirements in `docs/plan/uglycash-revamp-2026-10-07.md` (especially 173, 230–231, 261), the rewards/content rows of `reference-followthrough-2026-10-04.md`, and the remaining/social audits plus Task 6 brief. ## Assignment decision

**Create a separate Task 6B implementation for programmes plus content, with sequential sub-slices and explicit file ownership.** This is materially larger than a clubs amendment: persistent programme rules/entry/attribution/award/recovery, private messaging, content ingest/moderation and OAuth each have new authorization boundaries. Task 6 should deliver clubs and expose a membership authorization helper, membership-change events, and deletion integration. Task 7 should add navigation/settings/help/status links and common presentation integration only; Task 7B retains widgets/Live Activities. Task 4A–D own binary prediction execution; Task 4E owns Castora entry/claim; do not duplicate those as generic competitions. A single Task 6B implementer may deliver the slices serially; this recommendation does not authorize parallel edits or delegation.

Programmes cannot be closed as “external blocker” merely because their schema/service/UI is absent. Build these owners, migrations, authenticated flows, actual empty states, recovery and test adapters now. Activate only genuinely configured capabilities. Empty programme catalogues, news lists and conversation lists are valid real results; seeded public campaigns, earned amounts and messages are not.

- Extend `social/delete-data.ts`, reports/moderation target contracts, notification payload allowlists and app account/network cache cleanup deliberately with tests.

All writes carry an operation UUID, with DB uniqueness `(actor, network, action, operation_id)` and input digest. A same-key different payload returns conflict; retries return the original durable result. An actor-only operation lookup reconciles unknown timeouts. Use database transactions and durable uniqueness, not a process-local flight map, for cross-instance correctness. Server timestamps define boundaries; no financial floats. Cursor pagination uses `(created_at,id)` or a monotonic committed sequence consistently.

Capability response is a discriminated state (`active`, `inactive`, `paused`, `unavailable`) with stable reason code, last check and relevant approved rules/version. Do not overload an empty list or zero balance to mean disabled/error. Examples: `PROGRAMME_NOT_PUBLISHED`, `RULES_NOT_APPROVED`, `FUNDING_NOT_VERIFIED`, `SETTLEMENT_NOT_CONFIGURED`, `CONTENT_SOURCE_NOT_APPROVED`, `X_NOT_CONFIGURED`. Missing source implementation is an engineering TODO in the delivery report, never returned as a supposed provider refusal. Private queries include account+chain+entity in keys and clear/fence old results on sign-out, account/network switch, unlink and privacy change. Query status alone never establishes authorization.

## Programmes, referrals, rewards and competitions

### Persistent model

1. `programmes`: ID, kind (`referral`, `competition`, `reward`), chain/mode, optional club scope, draft/published/paused/closed lifecycle, immutable current rule-version reference, eligibility interval and owner/operator audit. No default active campaigns.
2. `programme_rule_versions`: immutable rules text/hash plus strictly validated machine schema: entry window, eligible assets/events, evidence source, eligibility constraints, scoring version, tie handling, finality cutoff, cancellation/disqualification/dispute procedures, reward specification and claim expiry if approved. Version changes cannot silently rewrite an entered campaign. Unknown rule types are unsupported/inactive, not executable arbitrary JSON/code.
3. `programme_entries`: unique programme/account entry, accepted rule version/time, status and eligibility evidence version; each mutation logged. `programme_evidence`: unique source+event+programme anchor, observed/finalized time/block, processing revision. Reorg/late evidence correction creates a new revision and invalidates provisional scoring.
4. `referral_codes` and `referral_attributions`: opaque random share code owned by account/programme, expiry/revocation; unique accepted invitee attribution per programme. Hash lookup values at rest; raw code only in intentional share payload and isolated local draft. A link open is a candidate, not acceptance or qualifying activity. Confirm attribution as the authenticated invitee against active rules; refuse self-referral, conflicting attribution and excluded accounts. Sender sees aggregate eligible counts only, not invitee balances/trades or hidden identities.
5. `programme_score_snapshots`: programme/rule/evidence version, period, as-of, provisional/final/disputed state and ranked entries. Privileged evidence may establish eligibility privately; publishing any identifiable financial metric separately requires Task 5 consent and club visibility. Permission narrowing invalidates public reads immediately across instances.
6. `reward_awards`: unique programme/entry/rule/evidence award identity, amount in integer units only if an approved rule supplies it, asset/chain, eligibility/held/claimable/settling/settled/expired/disputed state. `reward_settlements`: unique award, adapter, operation reference, external reference/tx hash, status and reconciliation checkpoints. `programme_disputes` and append-only operator actions record reason/evidence and outcomes; accounts cannot award themselves or alter evidence.
7. Funding reservations and liabilities are required for a payout adapter: reserve atomically against independently verified campaign funding before making an award claimable; prohibit duplicate allocation, negative reserves and cross-campaign spending. This is an internal accounting boundary, not a new treasury contract or authority to spend.

### API and native lifecycle

Implement catalogue/detail/rules, authenticated eligibility, entry and operation recovery, own entries/scores/rewards, referral issue/revoke/accept/status, award detail/claim/recovery and own dispute creation/status. Operator publication/rules/funding/dispute actions require a separate authorized operator policy with audit, not ordinary account auth. Unconfigured operator administration fails closed.

Native Programme detail reads actual rules, source and as-of; entry review fixes account/network/rule version then submits idempotently. Outcomes distinguish confirmed entry, refused eligibility, pending verification and unknown submission. Rewards shows `No awards` for actual empty data and `Unable to load` on failure. A valid claim review must show exact approved asset, amount, chain, destination, fee/gas, expiry and evidence before authorization. Revalidate all at claim time. Programme competitive entry has no invented entry fee, prize pool, APR or cashback. Score ties and anti-abuse thresholds are versioned rule inputs requiring approval, not arbitrary implementation constants masquerading as product policy.

Build an adapter interface (`capability`, `verifyFunding`, `prepare`, `submit`, `reconcile`) and a disabled production adapter that cannot submit. Use a deterministic adapter only in tests/local explicitly labelled development fixtures to verify the entire state machine. Wire actual existing voucher redemption only as its own authenticated voucher journey; never generalize its contract to repay awards. For a later funded adapter use the existing account/journal review pathway or a separately authorized backend signer policy. A timeout stays unknown and reconciles by durable reference before any second send. `submitted` is not `paid`; final settlement needs authoritative provider/chain evidence and reorg/finality policy.

This delivers complete source boundaries without manufacturing payout economics. Financial adapter activation remains unfulfilled until the actual funded mechanism and approved rules exist; report that precise remaining implementation/integration and approval work rather than calling all rewards complete.

## News

Implement a real database-backed catalogue and detail surface with zero production fixtures. `content_sources` holds operator-approved identity, canonical HTTPS origin, feed endpoint if any, rights/attribution/retention configuration, enabled state and last fetch status. `news_items` holds source/native ID uniqueness, canonical URL, factual title, permitted excerpt/body/media only, published/observed timestamps, instrument tags, revision and moderation state. `news_bookmarks` is account-private and optional but useful persistent native behavior.

Provide an operator-authenticated original editorial import path plus an RSS/Atom adapter that runs only for explicitly allowlisted approved sources. Do not choose a paid feed, scrape publisher pages or assume public RSS grants republication rights. Until source rights are known, no external article fields are ingested into production. First-party editorial entries can be original text with source links and attribution; never fabricate a launch catalogue. Ingest does not require a publisher login in the app.

Outbound fetch must prevent SSRF through private/link-local addresses, DNS rebinding and redirects; impose byte/time limits, disable XML external entities, sanitize markup, validate external URLs, and serve only permitted fields. Safe native link opening does not imply provider endorsement. No remote HTML execution or automatic tracking-image load. Route reads return source/as-of and an honest empty/unconfigured/stale/error distinction; stale retained content remains clearly timestamped. Corrections/retractions purge cached affected content. Extend reports with `news_item` and authenticated bookmarks with account erasure. Market news tags must map to real supported identifiers; no generated price-impact claim.

## Chat

Deliver actual first-party direct conversations and club rooms; external messaging providers are not required to build this. Reusing public thesis storage would leak private text. `conversations` identifies direct or club scope, chain, creation and closed state; `conversation_members` stores accepted/requested/left/removed status, role where needed, read cursor, notification preference and joined epoch. `messages` stores committed server sequence, author, bounded plain text, created/edited/deleted state and client operation UUID; direct pair uniqueness prevents duplicate concurrent threads. Add request/accept/decline, per-account rate budgets, reports and moderation actions. Text-only initial transport is an implementation milestone, not a declaration that any previously approved media scope is dropped.

Unknown senders create a request with a bounded first message; recipients accept before unrestricted exchange. Blocks deny new requests/sends in both directions; mute suppresses notifications. Direct reads require accepted/request participation according to explicit rules; private club room reads/sends require current active membership on every request. Default club history starts at membership epoch, unless an explicit approved club setting permits earlier history; removed members lose server access immediately. A leave/rejoin cannot bypass a ban or gain history accidentally. Operator access is audited and restricted to reported evidence, not a general public message endpoint. Do not claim end-to-end encryption: the proposed server stores readable messages for delivery/moderation.

Start with cursor polling and after-commit notifications; WebSocket optimization is optional and cannot be authorization authority. Every fetch/reconnect rechecks access. Outbox sends survive interruption under encrypted account/network-scoped storage, dedupe by operation ID and reconcile to server sequence. Distinguish sending/sent-to-service/failed/unknown/read (only actual recipient cursor); no fabricated delivered checkmarks. `markRead` advances monotonically only to accessible received sequence. Conversation list preview, unread counts, search and push must obey the same membership/block/privacy rules. Push defaults to generic “New message”; no body on lock screen. Clear plaintext caches/previews on sign-out or loss of membership; already viewed copies cannot be remotely erased.

Specify deletion truthfully: self-delete redacts message body with a tombstone; report evidence retention is separately protected and time-bounded by approved policy. Account deletion anonymizes/redacts owned conversation content and revokes access while preserving other participants’ permitted history and required abuse evidence. Native list/request/thread/composer must include pending/unknown retry, pagination, deleted/report/block, offline draft, keyboard, Back/resume and account-switch states.

## X linking

Implement identity linking only; no posting, DMs, follow actions or reward eligibility inferred from account linkage. An unverified manually typed X handle is not a linked identity. Prefer server-mediated OAuth callback with a registered HTTPS URL and native completion through a single-use opaque result handle; wallet session remains authoritative. Existing session is required both to start and consume completion.

`oauth_link_attempts`: random state hash, account, chain/session binding, PKCE verifier encrypted server-side, exact redirect, allowed return destination, expiry, consumed/status. `external_identities`: account/provider immutable subject uniqueness, display handle snapshot, verifiedAt, linked/unlinked state and separate public-visibility opt-in. Store credentials encrypted only for the shortest necessary exchange/revocation lifetime; identity-only linking need not request persistent refresh access. `oauth_revocations` is an encrypted retry job with bounded expiry if provider revoke is unavailable. Never log callback query strings, authorization codes, verifier or tokens.

Start → external authorization → callback validates unexpired single-use state → atomic attempt consumption/exchange → authenticated `/2/users/me` evidence → pending confirmation → same original app account confirms → linked. Replays, changed account/network, cancelled consent, denied scopes, provider timeout, exchanged-but-result-lost and duplicate external identity require distinct retry/reconcile states. Reject another account’s identity with a non-enumerating conflict, not automatic reassignment. Do not use X identity as wallet recovery/authentication. A backgrounded app can resume by its own attempt ID; bearer credentials never enter deep links or app storage.

Unlink immediately removes local/public linkage and prevents further usage; provider revocation retries separately and must not resurrect linkage. Show incomplete remote revocation honestly. Delete-data invokes the same path and deletes identity fields; residual token queue has only the restricted data needed to revoke until expiry. Link public display is off by default and cannot override an unlisted profile.

Verified protocol basis: X documents Authorization Code + PKCE, exact redirect matching, granular scopes, and optional `offline.access` for refresh tokens. Use S256. See [official X OAuth reference](https://docs.x.com/fundamentals/authentication/oauth-2-0/authorization-code) and [OAuth security BCP](https://www.rfc-editor.org/rfc/rfc9700.html). Before implementation activation, check the current official endpoint-to-scope mapping for `/2/users/me` and revocation endpoint/client authentication details; do not guess the minimal scope set or assume current account API entitlement. This audit did not inspect a developer console or credentials.
