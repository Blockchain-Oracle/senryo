## What the app actually trades

Senryo currently combines several distinct systems that the product does not explain well enough:

- Wallet funds are assets on a specific network. Receiving a token does not make it accepted trading collateral. Wrong-network or unsupported tokens do not create trading power.
- Original SenryoCore has configured AUSD/USDC collateral and account-level cross-margin risk (contracts/src/core/SenryoCore.sol, RiskModule.sol). The shared ticket pay planner can move supported dollars to trading; supported Mainnet assets require an actual executable conversion quote first. Practice uses test AUSD/USDC and has no universal aggregator. Do not promise deposit anything/use anything without route and conversion support.
- Perpl is a separate external crypto-perpetual venue with its own exchange/account/collateral/config/permissions. Source adapters exist; this continuation does not establish native authenticated provider acceptance. Native protection/controller/secure enrollment remains Task3B source work.
- Binary BTC/ETH shares, Castora numerical contests and leveraged pair positions have different payoff/collateral/settlement models. No single balance or leverage label can erase that distinction.

For a simple isolated illustration,100 collateral at5× targets500 of exposure; a1% price change is about5 PnL before fees/funding/slippage. In Senryo's current cross-margin model, account collateral supports positions together; the ticket amount is not an isolated maximum-loss guarantee. Leverage represents exposure, not500 of withdrawable borrowed tokens. The onchain risk module enforces initial/maintenance/fee/debt/hold constraints; source existence does not establish correct phone presentation or execution.

## Primary research and architecture direction

[Apple passkey guidance](https://support.apple.com/guide/iphone/use-passkeys-to-sign-in-to-websites-and-apps-iphf538ea8d0/27/ios/27) explains passkeys stored in Passwords/iCloud Keychain and verified with Face ID/Touch ID. [Apple biometric Keychain guidance](https://developer.apple.com/documentation/localauthentication/accessing-keychain-items-with-face-id-or-touch-id) supports direct biometric-gated item access. These are separate ceremonies. Recommended investigation: account-bound fresh biometric authorization for routine actions, passkey ceremony for account creation/recovery and genuinely required credential verification, with an explicitly reviewed authorization contract. Do not replace signatures with a cosmetic Face ID success or silently weaken current limits.

[Hyperliquid margining](https://hyperliquid.gitbook.io/hyperliquid-docs/trading/margining) provides a concrete trading reference: explicit cross/isolated modes, initial margin, mark price, maintenance and liquidation. [Its contract specifications](https://hyperliquid.gitbook.io/hyperliquid-docs/trading/contract-specifications) distinguish USDC collateral from the traded underlying and perpetual funding. This is a credible candidate for a future execution adapter, not an integration Senryo currently has. dYdX first-party materials were also checked, but the exact current margin documentation fetch failed; no implementation or current deposit-route recommendation is inferred from older pages. Perpl remains the existing external adapter to compare against alternatives. Select a venue only after real native deposit, order/fill, reduce/close, withdrawal, auth/recovery, source freshness, fees, eligibility and operational tests. Ecosystem consistency is not a reason to retain an inferior user experience.

[Official Ramp RN SDK](https://github.com/RampNetwork/ramp-sdk-rn) supports in-app integration with provider flow; a native wrapper does not itself prove payment, token arrival or a first-party Senryo checkout. Source currently uses the official SDK and separately records purchase versus delivery.

Product target: supported funding source → explicit conversion if needed → clearly named trading collateral/free margin → real order/fill/position → reduce/close → withdraw, with fees, price freshness, margin mode, liquidation, funding and recovery visible at the decision where they matter. Recommend proving one complete Practice route on physical phone first, then actual authorized live venue route. Keep Card, predictions, social and all approved scope, but these must not obscure the core acceptance gate.
